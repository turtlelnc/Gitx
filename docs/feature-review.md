# gitx 功能取舍与改进路线

## 产品边界

gitx 的核心用户是需要统一 Git 规范、但不希望记忆大量 Git 命令的中文小团队。功能只有满足至少一项时才应进入核心：

1. 明显降低高频 Git 操作的学习成本；
2. 落实可随仓库共享的团队规范；
3. 在合并、同步、认证等高风险操作前提供更安全的引导；
4. 为上述流程提供可选的 AI 辅助。

构建产物分发、通用文本编辑、完整终端 UI 等能力不属于这一边界。

## 保留功能

| 功能 | 必要性 | 结论 |
|---|---|---|
| `start` | 完成初始化/克隆并落地团队配置，是新手入口 | 保留 |
| `status` | 所有后续操作的决策依据，并统一显示仓库和分支信息 | 保留，优先改善可读性 |
| `save` / `save --ai` | 高频核心流程，也是提交规范的主要执行点 | 保留，增加选择性暂存 |
| `history` / `revert` / `explain` | 历史回溯、安全撤销与新手理解提交有价值 | 保留，改善展示与离线降级 |
| `branch` | 小团队并行开发必需 | 保留，补充安全删除和远端信息 |
| `integrate merge/rebase` | 冲突处理风险高，中文引导有明显价值 | 保留，补齐继续/中止/恢复 |
| `sync` | 远端协作必需 | 保留，改善 tracking、认证与非快进提示 |
| `stash` | 在切换、合并前临时保存改动有实际价值 | 保留，增加列表与选择恢复 |
| 团队配置与别名 | 是 gitx 区别于原生 Git 的核心能力 | 保留，采用成熟 TOML 解析器 |
| `doctor` | 能把身份、远端、SSH 等问题转成可执行提示 | 保留，增加机器可读输出 |
| `x` 扩展 | 将团队特有流程留在核心之外，避免再次膨胀 | 保留，增加首次信任确认 |
| `review --ai` | 对小团队缺少专职 reviewer 的情况有帮助 | 保留，增加隐私提示和文件筛选 |
| `changelog --ai` | 发布说明生成有价值 | 保留，支持范围和输出文件 |
| `pr create --ai` | PR 文案有价值，但当前并不创建 PR | 保留能力，改名为 `pr draft --ai` 或真正接入平台 API |

## 已移除功能

| 功能 | 移除原因 | 替代方案 |
|---|---|---|
| `bundle create` | 属于发布/打包领域，平台耦合与安全维护成本高，偏离 Git 协作主线 | CPack、GitHub Releases、系统安装包或团队扩展脚本 |
| `gitx tui` | 功能不完整，重复成熟 Git TUI，终端兼容成本高 | lazygit、tig、IDE Git 面板 |
| `gitx edit` | 编辑器体验难以达到可用标准，重复用户已有工具 | `GIT_EDITOR`、`VISUAL`、`EDITOR` |
| `open` | 名称暗示“打开项目”，实际只打印路径和分支 | 信息并入 `status` |
| `tag` | 仅能创建，不能列出、删除或推送，无法形成完整工作流 | 暂用原生 `git tag`；实现完整生命周期后再评估 |

## 改进优先级

### P0：让核心流程可信

- 已完成：`status` 以“已暂存/未暂存 + 新增/修改/删除”等中文状态替代 libgit2 数字位掩码。
- 已完成：`save --all` 暂存全部；`save <文件...> -- <提交信息>` 只暂存指定文件；默认只提交已有暂存区。
- 已完成：没有 `user.name` / `user.email` 时拒绝提交；`gitx config user set` 管理当前仓库署名。临时设备署名必须由 `gitx config user temporary` 显式启用，后续不会自动重写历史。
- 已完成：`revert <提交号>` 以反向提交回退普通提交；不实现会改写共享历史的 reset，冲突时保持仓库不变。
- 合并和变基增加明确的 `--continue`、`--abort`，并在异常退出后由 `doctor` 识别未完成状态。

### P1：让协作流程完整

- 已完成：`sync push/publish` 会建立当前分支 upstream；重复 `publish` 仅在 URL 相同情况下复用 origin，改地址需显式 `sync set-origin`。克隆会恢复服务器 HEAD 错指空分支的常见情形，避免创建无关根历史。
- `pull` 明确支持 `--ff-only` 或 `--rebase`，不要把所有非快进情况归为同一错误。
- HTTPS 凭据接入系统凭据库，并支持 Git credential helper，而不只依赖环境变量。
- AI 请求前显示 provider、将要发送的文件和截断情况；支持排除密钥文件、二进制文件和路径规则。
- 将手写 TOML/JSON 解析替换为成熟库，避免复杂字符串、Unicode 和响应结构产生静默误判。
- 项目级 `x` 脚本首次运行时显示路径并确认信任，支持按内容哈希记住决定。

### 本轮实测补充

- `doctor` 分别诊断 SSH 私钥文件与 SSH agent 是否实际加载密钥；仅有私钥文件不再被误报为可推送。
- bare 服务器应将 `HEAD` 指向实际默认分支（通常为 `main`）。Gitx 对单一远端分支会尝试恢复，但多分支且 HEAD 无效时应拒绝猜测。

### P2：提升日常体验

- `history` 增加日期、分支/标签、`--oneline` 和分页；`explain` 在无 AI 时输出结构化本地摘要。
- `stash` 增加 `list`、按编号 `pop/apply/drop`，并默认包含未跟踪文件时明确提示。
- 无参数向导根据仓库状态动态给出下一步，而不是固定菜单；在仓库外直接提供 `start` / `clone`。
- `config` 增加 `show`、`validate` 和字段级错误位置，便于 CI 在合并前校验团队规则。

## 暂不进入核心的能力

发布打包、完整 PR 平台管理、代码托管平台 issue 管理、通用文件编辑器和全屏 Git UI 应优先以 `gitx x` 扩展或外部工具提供。只有当团队规范确实需要统一这些能力，且能够形成跨平台、可测试的完整工作流时，再考虑进入核心。
